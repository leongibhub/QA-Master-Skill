## Shared setup, data, oracles and cleanup

`A`/`B` below are symbolic isolated test tenants, not existing environments. `W_A`, `R_A`, `P_A` denote usable bearer-token fixtures with only document:write, document:read, document:publish respectively in tenant A. `RW_A` combines read/write; `ALL_A` combines the three for the lifecycle journey. `NONE_A` has none. Tenant B needs equivalent controlled fixtures. These are proposed fixtures; tokens, role assignment mechanism and accounts are unknown and must not be requested/used in this task.

A baseline body is `{"title":"Draft A","body":"Body A"}`. An edit body is `{"title":"Draft B","body":"Body B"}`. `repeat("a",n)` means n ASCII characters, generated separately for each variant. A normal fresh key is an independently allocated 16-character ASCII string; `qa-key-000000001a` is a shape example only. Fresh-key uniqueness across runs requires an approved allocation method. JSON requests use application/json. `d` is an actual ID supplied by a future controlled fixture, `v` its observed current integer version. Headers are bearer authorization, Idempotency-Key on create, If-Match on edit/publish. Header integer serialization follows the draft's integer contract; ETag quoting, weak tags and wildcard semantics are not specified.

Success schema S: response object contains nonempty string id, string title, string body, state DRAFT or PUBLISHED, integer version >=1 (A schemas/Document). No tenant/timestamp/notification field or prohibition on extra response fields is assumed. H: X-Request-ID is present with nonempty string value (A headers/RequestId). H applies to every listed response and every documented status; no ID uniqueness, UUID format, echoing or log-join guarantee is inferred. Denial bodies are unconstrained.

Readiness `DRAFT-RULE` = a bounded expected result is source-defined, subject to common execution blockers G08/G09/G15 and any row-specific gaps. `PARTIAL` = some assertions are defined but an observable or oracle is missing. `CONDITIONAL` = no complete pass/fail oracle until the stated decision. These are descriptive readiness labels, not Gate/evidence statuses.

Cleanup C-M: no cleanup action now (offline design); future execution would create/change documents and may emit unknown events. Approved reset/disposal and side-effect handling are missing (G09); do not invent DELETE. Preserve IDs/request IDs for authorized cleanup. Cleanup C-R: request itself is intended read-only; no document cleanup for that action, but fixture teardown still needs C-M. Cleanup C-N: no intentional mutation; future invalid/denied requests need permitted unexpected-effect inspection before C-M; a denial status alone does not prove no effects. Every case below explicitly chooses a cleanup type.

Automation candidate `API` means suitable for an authorized API harness once fixtures/oracles exist, not a supplied executable script. `API+OBS` also needs approved persistence/event observations. `PLAN` means scenario outline awaiting material facts. No expected-result row asserts generic absence of all side effects unless R explicitly promises it.
