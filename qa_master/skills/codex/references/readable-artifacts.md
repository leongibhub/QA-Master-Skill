# 可读的测试用例与缺陷草稿

面向第一次参与 QA 的读者：先让人看懂场景，再保留机器需要的 ID、错误码和原始证据。用用户的语言写作；项目或跟踪系统要求的字段仍须保留。此约定适用于新写、改写、评审的测试用例、缺陷草稿，以及准备导入或提交到跟踪系统的包；它不授权执行测试或外部写入。

先读取需求、设计、代码、接口契约或已提供观察。没有来源的内容不要补全。状态可写中文（如“草稿”“待复现”“已观察”），但既有契约要求的 `NOT_EXECUTED`、`OBSERVED`、用例 ID、接口路径和错误码必须原样保留。

摘要只是呈现方式，不是删字段的许可。项目、跟踪系统或 schema 要求的风险、类型、优先级、oracle、自动化、批准和其他机器字段，必须在用例/缺陷详情或紧凑的机器元数据中原样保留；不要删除、改名或用自然语言替代。

普通人读的用例和缺陷正文不要主动展示未经要求的 `source_role`、`direct_input`、`Trace`、`systemstate` 等元数据键，也不要编造合成 trace ID。保留实际已提供的 ID、可读来源、必要的精确命令和字面值。若已提供的 API、领域或响应字段本身就名为 `source_role` 或 `Trace`，它是相关事实，必须原样留在相关步骤或预期中，不是未经要求的元数据。只有制品或导入元数据被用户、项目或 schema 明确要求时，才在单独的机器 payload/技术支持块中原样保留；不要删除或改名。

只要求一个或几个用例/缺陷时，直接交付这些详情和相关缺口；单个用例不必先做摘要表，批量时摘要表才是可选导航。除非用户提出或项目契约要求，不要默认附上完整 QA 策略、十三维度覆盖矩阵、JSON 交接包或路由分析。

## 写用例

标题使用“条件 + 结果”，例如“缺少序列号的设备清单被拒绝导入”，而不是“导入测试”。先列出已知环境、账号权限、初始状态和数据；只写来源已经给出的内容。

用例清单只做摘要；不要把操作步骤和预期挤进元数据大表：

| ID | 标题 | 状态 |
| --- | --- | --- |
| TC-001 | 缺少序列号的设备清单被拒绝导入 | 草稿 / `NOT_EXECUTED` |

默认每个用例直接用以下详情交付。明确要求的项目格式可替代此表，但必须保留每个编号动作与预期结果的一对一对应：

```text
## TC-001 — 条件 + 结果
来源：<需求、接口契约或代码位置>
已知环境与数据：<版本、权限、初始状态、输入；仅已提供事实>

| 步骤 | 操作步骤 | 预期结果 |
| --- | --- | --- |
| 1 | <一个操作> | <这个操作可观察的结果，以及已知依据> |
| 2 | <下一个操作> | <这个操作可观察的结果，以及已知依据> |

收尾：<已知的恢复动作；没有则写“未提供”>
待确认：<具体缺什么；会影响哪一步或哪条预期>。
状态：草稿 / `NOT_EXECUTED`
```

一行只放一个动作；每个编号动作（包括准备）都有自己的预期结果。准备步骤的结果可写为已知的前置状态；如果该步骤的预期未知，直接写“待确认：具体缺什么，影响第几步”，不要给它编造输入回显、脱敏、错误状态或副作用。不要为了显得完整而编造中间页面、按钮、阈值、提示文案、账号、凭据或执行证据。性能阈值未给出时，写“待确认：通过阈值，影响第几步”，不要猜数值。

## 写缺陷

标题写“症状”，例如“缺少序列号的清单仍被导入”，不写未证实的根因。缺陷草稿至少包含：

```text
## BUG-001 — 症状
环境与前提：<构建/版本、平台、账号或数据；仅已知事实>
复现步骤：
1. <一个操作>。
2. <一个操作>。

实际结果：<保留已提供/已报告的观察并标明来源；Agent 未复现时写明“Agent 未复现”>。没有观察时写“待复现/未提供实际结果”。
预期结果：<来源规定的行为；没有则写待确认>。
影响：<已知用户、数据或流程影响；未知则写“待确认：影响范围”>。
证据：<可定位的日志、截图、命令输出、时间或哈希；未提供则写“待确认：复现证据”>。
状态：草稿 / 待复现 / 已观察；保留 `NOT_EXECUTED` 或 `OBSERVED`（如适用）。
```

不要把猜测写成原因、严重性、发生频率或已修复结论。用户提供或外部报告的观察应保留来源，不能因 Agent 未执行而删除；但也不能把它改写为 Agent 已观察。没有观察时是草稿或待复现，不是已确认缺陷；不要关闭缺陷或声称回归通过。

## 虚构示例（只演示写法）

以下不是产品事实、执行记录或缺陷证据。

```text
## TC-DEMO-001 — 缺少序列号的设备清单被拒绝导入
来源：虚构接口说明中的规则 SERIAL_REQUIRED。
已知环境与数据：虚构命令 inventory-import；输入 fixtures/missing-serial.csv 缺少 serial_number。

| 步骤 | 操作步骤 | 预期结果 |
| --- | --- | --- |
| 1 | 运行 inventory-import --file fixtures/missing-serial.csv | 返回 SERIAL_REQUIRED，且不创建设备记录。 |

收尾：未提供。
状态：草稿 / NOT_EXECUTED。

另有一条虚构用户报告：命令返回 `IMPORT_OK`，并创建 1 条设备记录；该报告未经 Agent 复现。

## BUG-DEMO-001 — 缺少序列号的清单仍被导入
环境与前提：虚构构建 demo-2026.10；使用同一缺少 serial_number 的文件。
复现步骤：
1. 运行 inventory-import --file fixtures/missing-serial.csv。

实际结果：用户报告：返回 IMPORT_OK，并创建 1 条设备记录；Agent 未复现。
预期结果：返回 SERIAL_REQUIRED，且不创建设备记录。
影响：已报告会创建不完整设备记录；待确认：实际影响范围。
证据：待确认：用户报告对应的命令输出或日志位置。
状态：草稿 / NOT_EXECUTED；用户报告，Agent 未复现。
```

## 技术支持信息

与当前动作或预期有关的精确命令、API 路径、值和单位、错误码、实际 ID 必须留在相应步骤或预期旁边。把过长的原始请求/响应摘录、项目要求的跟踪 ID、证据哈希和时间元数据放进“技术支持信息”小节，保持紧凑且可定位。首次使用必要术语时先解释，例如“幂等键：重复提交时用于约束副作用次数的标识”。不要删除来源或上下文来换取简短；也不要把原始数据堆砌成对读者没有解释的正文。

## 交付前检查

- 标题是否说明条件和结果，或缺陷症状？
- 已知环境、数据、来源和权限是否明确，未知是否写成“待确认：具体缺什么/影响哪步”？
- 默认表格是否为“步骤 | 操作步骤 | 预期结果”，且每个编号动作（包括准备）都有预期或精确的“待确认：具体缺什么，影响第几步”？
- 预期与实际是否分开，原始技术事实是否保留且易定位？
- 是否没有虚构界面、阈值、凭据、执行、原因、频率、严重性或结论？

格式清晰不等于用例正确、缺陷成立、已批准、已导入或已执行。完成事实核对和必要人工审阅后，才可作为交付候选。
